# Piano Sync — 디자인 원칙

> 대상: **PWA 웹 에디션**(모바일 설치형 웹앱). 데스크톱 PySide6 앱은 이 문서의 범위가 아니다.
> 이 문서는 구현(`pianosync/web/static/`)과 함께 유지된다.

## 1. 디자인 방향

**“정밀한 스튜디오 콘솔” (Precise Studio Console)**

연주 비교는 ‘감상’이 아니라 ‘확인’에 가깝다. 사용자는 두 연주가 **어디서 어긋나는지**를 빠르게 판단하고, 전환 지점을 확정한 뒤 결과물을 내보낸다. 그래서 화면은 감성적 장식보다 **측정·대조·정확성**을 시각적으로 전달한다.

- 모노크롬 구조(거의 검정/거의 흰색) + 1px 규칙선
- 숫자는 모노스페이스·tabular-nums
- 색은 **데이터(연주 레인)와 상태**에만 절제해서 사용
- 그림자·블러는 팝오버/시트에만

## 2. 제품 정의

| 항목 | 정의 |
|---|---|
| Purpose | 같은 곡을 연주한 2~5개 영상을 음악적으로 정렬하고, 전환 지점을 확인해 비교 영상으로 내보낸다. |
| Audience | 음악 교사/학생, 연주자, 합주 리뷰어. 주로 데스크톱에서 준비하고 **모바일에서 확인·간단 편집·내보내기**. |
| Brand personality | 정밀함, 차분함, 신뢰, ‘악기 같은 도구’. 과장·유행 지양. |
| Primary device | 360–430px 스마트폰, 768px 태블릿, 1280px+ 데스크톱. |

## 3. 정보 위계

1. **소스와 분석 상태** — 무엇을 비교 중인지, 분석이 됐는지
2. **정렬 타임라인 + 구간** — 실제 정렬 결과(가장 중요한 검증 정보)
3. **전환/출력 설정** — 결과물에 영향을 주는 조정
4. **결과** — 렌더 진행, 미리보기, 다운로드

모바일에서는 1→2를 한 화면(스텝 1)에 두어 스크롤로 이어지게 하고, 3→4는 스텝 2로 분리한다.

## 4. 탐색 모델

- **2단계 워크플로**: ① 소스·정렬 ② 내보내기
- 데스크톱: 좌측 레일(스텝 + 소스 목록 + 엔진 표기)
- 모바일(≤760px): 상단 가로 스텝 바, 보조 정보(소스 목록·엔진)는 숨김
- 설정은 **모달 시트**(모바일에선 하단 시트)로 분리 — 작업 화면을 가리지 않음

## 5. 상호작용 모델

- 타임라인: 드래그/탭으로 재생 위치 이동, ←/→ 키로 10ms(Shift 100ms)
- 구간/레일 소스: 탭(또는 Enter/Space)으로 이동
- 설정 변경은 자동 반영(전환 설정은 디바운스 후 재계산)
- 파괴적 동작(소스 제거)은 즉시 실행되며 토스트로 피드백

## 6. 반응형 / 적응형

- 브레이크포인트: `≤940px` 2열→1열, `≤760px` 레일→상단 바·시트형 설정
- `viewport-fit=cover` + `env(safe-area-inset-*)`로 노치/홈 인디케이터 대응
- `100dvh`로 모바일 주소창 높이 변화 대응
- 고정 픽셀 위치 대신 grid/flex·clamp 사용
- 텍스트를 무리하게 축소하지 않음(최소 12px 캡션)

## 7. 접근성 원칙

- 터치 타깃: **Apple HIG 44pt / Material 3 48dp** 기준. coarse pointer에서 44px 이상 보장.
- 명도 대비: 본문/캡션 AA(4.5:1), 비텍스트 UI 3:1 이상 (아래 ACCESSIBILITY.md에 실측값).
- 색만으로 상태를 전달하지 않음(텍스트/아이콘/패턴 병행).
- 키보드 포커스 표시(`:focus-visible`), Enter/Space 동작.
- `prefers-reduced-motion` 존중.
- 아이콘 전용 버튼은 `aria-label`, 라이브 영역(`role=status`)으로 알림.

## 8. 의도적으로 하지 않는 것 (Restraint)

- 보라색 그라데이션, 과한 글래스모피즘, 장식용 블러/그림자
- 모든 콘텐츠를 카드로 감싸기 (설정 그룹·리스트 등 의미 단위에만 카드 사용)
- 의미 없는 아이콘, 이모지 아이콘
- 콘텐츠보다 앞서는 애니메이션
- 작은 화면에서 정보 과밀 노출
- 기능이 연결되지 않은 버튼을 완성된 기능처럼 표시하기

## 9. 참고 자료 (조사 범위 명시)

공식 지침(2026-10 기준 확인):
- Apple Human Interface Guidelines — Hit Targets: **44×44pt 이상** (https://developer.apple.com/design/tips/)
- Material Design 3 — Touch targets: **48×48dp 권장, 8dp 간격** (https://m3.material.io/foundations/designing/structure)
- Android 접근성 — 터치 타깃 48dp (https://support.google.com/accessibility/android/answer/7101858)

웹 표준:
- CSS `env(safe-area-inset-*)`, `100dvh`, `prefers-reduced-motion`, `prefers-color-scheme` (MDN)

**미검증/한계**
- 실제 서비스 앱 화면을 스크린샷으로 직접 대조하지는 않았다(문서 요약 기반).
- iOS/Android 네이티브 컴포넌트가 아니라 **웹(PWA)** 구현이므로 플랫폼 컴포넌트 자체를 쓰지는 않는다. 관습(타깃 크기·안전 영역·뒤로가기/스크롤)만 차용한다.
- 스크린샷을 사람이 육안 검수하지 못하는 환경 제약이 있어, 레이아웃은 DOM 계측(오버플로우·겹침·타깃 크기·대비 계산)으로 검증했다.
